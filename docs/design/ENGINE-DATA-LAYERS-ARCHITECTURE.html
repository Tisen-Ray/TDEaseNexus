TDEASENEXUS · BACKEND ENGINE · DATA LAYERS

数据落在哪、谁是真值

三类字节：用户自己的 Workspace、Backend 数据根里的 Run 与目录、客户端 System 状态。真值只有两处，其余都是派生物或副本。

两处真值

别的都可以丢，这两个不行

  • Workspace：用户自己的目录，产品从不把它当作可清理的缓存。
  • run.json + events.jsonl：Run 的不可变定义与生命周期唯一事实；SQLite 只是它的投影，坏了就从事件重放。
  • nodes/<id>：可执行身份 = 目录内容 sha256；Run 按 id 绑定节点，执行用的是 catalog 当前持有的字节 —— digest 是 provenance（进 Run 记录），不是执行期强制（node_catalog.py）。

Run 目录里的字节从哪来

三种物化

  • 本地 Workspace：控制文件复制，其余先进入 Backend CAS，再从 immutable blob hardlink。
  • 节点包：留在 Backend catalog，经 config["nodes"] 绝对路径注入，不进 Run 目录。
  • 远端/上传输入：从 blob store 内容寻址取回。

还没收口的地方

两条静默路径

  • CAS / snapshot 在显式 purge 后才进入回收流程，并保留宽限期以避免并发上传误删。
  • 没有按 digest 的 immutable snapshot：Run 绑定的是节点 id，执行用 catalog 当前字节；替换 catalog 会影响后续执行 —— digest 只作为 provenance 记录在 Run 里，从不构成执行隔离（node_catalog.py）。
